# SOUL 增量写入协议

## 什么时候写

只有新信息能够跨任务复用时才写入 SOUL。一次页面加载失败、临时实验数据、某帖表现和过程日志留在对应 Model Memory。

## 怎么写

1. 先读当前字段，避免用更弱证据覆盖更强证据。
2. 只改本轮获得新证据的条目；不要为了格式整齐填满其他占位符。
3. 使用以下标记表达认识状态：
   - `已验证`：有代码、页面、数据或用户明确陈述支持；
   - `暂定`：存在多个一致信号，但还没有真实使用或结果验证；
   - `假设`：当前 loop 为推进工作提出；
   - `未知`：证据不足。
4. 在“证据与假设”部分记录简短来源，例如本地相对路径、产品 URL、Memory 截图/报告或“用户陈述 YYYY-MM-DD”。
5. 更新“最近更新”时间；不要把逐次操作日志堆进 SOUL。

## 不允许的推断

- 从路由名或按钮名直接推断核心用户。
- 从功能存在直接推断用户痛点、使用频率或付费意愿。
- 从宣传文案直接认定真实能力。
- 从单次截图直接推断完整流程。
- 从一次内容表现直接改写产品价值主张。

## 典型增量

首次读代码时可以写：产品是 Web 应用；存在上传、项目列表和结果页面；具体用户与核心问题未知。

完成一次真实任务后可以补：某能力已在真实页面走通；用户在哪一步需要人工判断；该任务是否确实解决了用户陈述的问题。

完成市场或结果验证后才可以逐步写入：稳定用户场景、核心任务、价值主张和差异化。证据不足时继续保留假设。
