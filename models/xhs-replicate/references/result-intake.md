# 结果回收与复盘

这是 `xhs-replicate` loop 的内部阶段，不是独立 Skill。只在用户要求复盘，或主动提供发布结果时执行；数据回收节奏由人决定。

## 状态检查

每次从文件系统重新检查，不维护额外状态：

```bash
ls memory/xhs-replicate/publish-log/$(date +%Y-%m).md
ls -t memory/xhs-replicate/publish-log/*.md | head -3
```

- 当月日志不存在：询问用户是否已回收 24h/48h/7d 数据以及从哪里读取。
- 最近三个月不足三份：说明证据仍少，不把趋势写成稳定规律。
- 日志存在但时间点不完整：只分析已观测窗口，明确标注缺失项。

## 发布日志模板

日志按月写入 `memory/xhs-replicate/publish-log/YYYY-MM.md`，每条发布追加一个 entry：

```markdown

- 归类：爆 / 平 / 限流 / 证据不足
```

## 分析流程

1. 读取本周或本月记录，先按可比较的账号、主题、发布时间和观测窗口分组。
2. 在各自基线内归为“爆 / 平 / 限流 / 证据不足”，不要跨账号直接比较绝对阅读量。
3. 对照本 loop 现有方法，找出被加强、被反例推翻和新出现的信号，包括钩子、结构、词汇、形式、发布时间与风险信号。
4. 单条数据只能形成观察；至少 3 条可比记录共现，才可提出新规律。
5. 在对话中给出方法变更 diff，列出每条建议对应的 note、窗口和指标。用户确认后，更新拥有该方法的 Model、Collector 或 Executor；不要把方法写进 Memory。
6. 推翻旧规律时保留退役记录，注明日期、原因和证据，不抹掉历史。

## 输出

- 当前窗口的数据完整度与不可比项。
- 爆 / 平 / 限流 / 证据不足的分类表。
- 被加强、被推翻、新出现的信号及证据。
- 下一轮内容与采集建议。
- 等待用户确认的方法 diff。

发布日志、截图和单帖复盘是 Memory；本文件及确认后的流程规则是 Model 方法。两者不得混放。
