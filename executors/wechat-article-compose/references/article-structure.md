# article-structure · 公众号长文结构

公众号默认按“读者问题”组织，不按产品功能清单组织。

## 推荐结构

1. **开头 150 字内讲清问题**
   不铺垫行业大词。直接写读者正在卡什么、为什么这个问题值得今天解决。

2. **先给判断，再展开理由**
   公众号读者愿意读长文，但不愿意等结论。第二屏前给出主张：这篇到底建议怎么做。

3. **方法分层，每层有可执行动作**
   每节用“问题 → 做法 → 例子/截图 → 注意点”。小标题要能单独被目录扫描。

4. **产品出现要服务于方法**
   写“用这个产品可以把这一步变成什么结果”，不要写“产品有某功能”。

5. **收尾给下一步**
   引导去体验产品、保存模板、参与调研等。CTA 要具体，不喊口号。

## 常用文章类型

| 类型 | 适用场景 | 骨架 |
|---|---|---|
| 教程 | 功能教学 / 方法论 | 问题 → 步骤 → 截图 → 注意点 |
| 案例 | 展示真实工作流 | 背景 → 输入 → 过程 → 产物 → 复盘 |
| 观点 | 产品/行业判断 | 现象 → 判断 → 证据 → 启发 |
| 更新 | 功能发布 | 用户痛点 → 新能力 → 如何使用 → 边界 |

## 硬规则

- 每篇只解决一个主问题。
- 小标题连起来就是文章摘要。
- 产品截图必须是真实截图，不让 AI 伪造 UI。
- 能力、信源与边界以 `SOUL.md`、产品代码或可见产品行为为准。
